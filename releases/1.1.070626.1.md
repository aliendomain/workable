# 1.1.070626.1

Date: 2026-07-06

## Added

- Added a public in-process workflow command surface through `IWorkflowCommandDispatcher` for backend and library callers that need to start workflows or operate workflow runs without going through HTTP routes.
- Added `WorkflowCommandOptions`, `WorkflowCommandResult`, `WorkflowCommandStatus`, `WorkflowCommandRun`, `WorkflowCommandStep`, and `WorkflowRunAction` contracts for command dispatch, accepted/completed outcomes, authorization failures, and authorized run snapshots.
- Added default-system and named-system workflow command dispatch so callers can target the same Workable systems used by worker command dispatch.
- Added `IHttpContextWorkflowCommandDispatcher` for ASP.NET Core hosts that want workflow command dispatch using the current HTTP request context.

## Changed

- Routed the built-in workflow HTTP start and action routes through the shared in-process workflow command dispatcher so HTTP and backend command paths use the same command behavior.
- Updated workflow docs to describe the in-process workflow command surface and avoid referring to it as a separate backend surface.

## Fixed

- Preserved authorized completed workflow run snapshots in HTTP wait-for-completion responses even when the runtime can no longer rehydrate the run by id.
- Prevented unauthorized HTTP workflow action responses from hydrating and serializing workflow run details by id.
- Expanded workflow command and HTTP adapter test coverage for command status mapping, named systems, wait behavior, authorization, action handling, and command-result snapshots.
